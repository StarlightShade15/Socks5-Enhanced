Protocol field guide / 01SOCKS5 · Authentication
A small, testable milestone

Make the client prove who it is.

SOCKS5 authentication happens after the TCP connection and before the client asks the proxy to connect anywhere. This guide covers the greeting and required username/password exchange only.

Your server today
TCP accept + read

The listener works. It still needs to parse SOCKS5 bytes and send protocol replies.

The exchange

Each arrow is a separate message on the same TCP connection. Read the required number of bytes; one read is not guaranteed to return a whole message.

  1. 01
    Client → server · method offer

    Client greeting

    The client identifies SOCKS version 5, says how many methods it is offering, then lists those methods. Method 02 means username/password.

    05 01 02Version 5 · one method · username/password
  2. 02
    Server → client · method choice

    Require authentication

    If the client offered method 02, select it, even if it also offered methods you don’t support. If 02 was not offered, send the rejection below and close the connection. Never select 00 (no authentication).

    05 02Choose SOCKS5 username/password authentication
    05 FFNo offered method is acceptable; close the connection
  3. 03
    Client → server · credentials

    Username/password request

    This sub-protocol has version 01. Each credential is prefixed by a one-byte length; the bytes are not null-terminated strings.

    01 · ULEN · UNAME · PLEN · PASSWDExample: 01 04 alex 06 secret
  4. 04
    Server → client · authentication result

    Check and answer

    Validate the version and lengths, compare both credentials, then send the result. On failure, close the connection; don’t continue to a request.

    01 00Success · use 01 01 for failure

Read the fields

  • VERGreeting version: 05.
  • NMETHODSHow many method bytes follow.
  • METHODSRead exactly that many bytes; look for 02.
  • ULEN / PLENOne-byte lengths, from 1 through 255.
  • UNAME / PASSWDRead exactly each length; then compare with configured credentials.

Implementation order

  • FirstGive the handler access to the expected username and password.
  • ThenRead the greeting header, followed by its method list.
  • NextSelect only method 02; reject clients that did not offer it.
  • ThenRead the auth fields by their lengths and send success or failure.
  • FinallyTest correct credentials and wrong credentials separately.
Important: this authentication is not encrypted.

SOCKS5 username/password credentials travel as readable bytes. Keep the listener on 127.0.0.1 while learning; don’t expose it to an untrusted network. Never print passwords in logs.

Connect it to your project

Update the test client after the server replies

Your Requests test currently has no proxy credentials. Once the server requires authentication, configure its SOCKS URL with the username and password. Keep the socks5h scheme so the proxy resolves the destination hostname. Encode special characters in credentials before putting them in a URL. An HTTPS request still needs the later CONNECT and data-relay stages; this authentication milestone alone won’t make the full request pass.

That 05 FF reply rejects authentication methods during greeting negotiation. Later, if a client sends an unsupported SOCKS command, that is a different reply: the request response code is 07 (“command not supported”).
